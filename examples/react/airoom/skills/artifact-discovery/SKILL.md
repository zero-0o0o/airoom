# Artifact Discovery

Use this skill to identify files and directories generated by AI tools, inspect existing entries in `airoom/registry.yaml`, detect discrepancies, and evaluate whether artifacts can be organized under `airoom/artifacts/`.

Discovery is strictly read-only: do not register, move, rename, edit, or delete anything while using this skill.

## Workflow

1. **Read Project Context**:
   - Read `airoom/AIROOM.md` and `airoom/registry.yaml`.
   - Treat registry entries as claims to verify against the filesystem.

2. **Inspect the Filesystem**:
   - Inspect `airoom/artifacts/` for existing managed artifacts.
   - Inspect the project root for unorganized AI tool outputs and candidate directories.
   - Do not perform unbounded deep recursive scans across the entire filesystem; focus on project root, configuration files, and suspected tool output locations.

3. **Symlink Handling**:
   - Treat symlinks as opaque.
   - Never follow symlinks to inspect target contents.
   - Report symlinks as symlinks without altering them.

4. **Identify Candidate AI Artifacts & Owners**:
   - Look for well-known AI tool signatures:
     - **Graphify**: `graphify-out/`, `.graphify_*`
     - **Superpowers**: `docs/superpowers/`, `.superpowers/`
     - **Assistant Scratchpads & Caches**: `.claude/`, `.aider*`, `.cursor/`, brainstorm logs, LLM plan/spec folders.
   - Check evidence for tool ownership:
     - Project skills (`.agents/skills/`, `.cursor/rules/`, etc.)
     - Configuration files (`pyproject.toml`, `package.json`, environment files)
     - File contents and headers (generated-by markers, tool version tags)
     - Git commit history or recent command invocations.
   - Distinguish AI tool outputs from:
     - Core project source code and user files (e.g. Rust, Flutter, Go, Python, Node, etc.)
     - Standard package dependencies (`node_modules/`, `.venv/`, `vendor/`)
     - Build artifacts (`build/`, `dist/`, `target/`, `.cache/`)
     - Version control (`.git/`)

5. **Evaluate Relocation Feasibility**:
   - Determine if the owning tool supports custom output paths via environment variables (e.g. `GRAPHIFY_OUT`), CLI options, or project skills.
   - Determine if the candidate is a standalone document/spec that can safely reside under `airoom/artifacts/`.
   - If the tool requires a hardcoded project-root path or compatibility cannot be verified, classify it as candidate for `management: external`.

6. **Detect Registry Discrepancies**:
   - **Missing Registered Paths**: Entries in `registry.yaml` whose `path` does not exist on disk.
   - **Unregistered Candidates**: AI tool outputs on disk that have no corresponding entry in `registry.yaml`.
   - **Type Mismatches**: Entries declared as `file` that are directories on disk, or vice versa.
   - **Placement Mismatches**: Entries marked `management: managed` whose `path` does not start with `airoom/artifacts/`.
   - **Duplicate Claims**: Multiple entries pointing to the same disk path.

## Discovery Report Format

Provide a clear, structured summary:
- **Inspected Locations**: Directories and configuration paths checked.
- **Existing Registered Artifacts**: Verification status of active registry entries.
- **Unregistered AI Candidates**:
  - Path
  - Likely Owner / Evidence
  - Type (`file` or `directory`)
  - Recommended Mode (`managed` via `artifact-organization` vs `external` via `registry-management`)
  - Relocation Feasibility Assessment (supported env var, skill adaptation, or hardcoded)
- **Registry Discrepancies**: Missing paths, mismatches, or invalid paths found.
- **Recommended Next Steps**: Whether to invoke `artifact-organization` for relocatable artifacts or `registry-management` for external tracking.
